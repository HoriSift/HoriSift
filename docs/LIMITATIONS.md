# Limitations and uncertainty policy

HoriSift has internal discovery, parsing, conservative Horizon detection, 25 versioned source-backed migration rules and a deterministic static risk-triage engine; there is still no published npm package, public CLI, final report renderer, site, or actual application migration validation. Proposed CLI commands remain designs, not shipped behavior.

Once implemented, static source analysis cannot reliably resolve runtime-generated URLs, arbitrary wrappers, plugin loaders, cross-repository code, inferred provider behavior, or every historical Stellar SDK variant. A zero-finding report is **not** proof of migration readiness. An incomplete scan must be declared as such.

Stellar RPC retains bounded history (provider-dependent). Horizon's historical indexing, HAL schema, and streaming behavior are not automatically available via RPC. Even documented RPC method mappings may require ledger-entry reconstruction, transaction XDR processing, separate indexing, provider options, and human review. The project is unaudited. Reports must not include secrets or raw source by default.

File discovery deliberately skips symbolic links, ignores common build/vendor directories and optional literal excluded paths (not `.gitignore` glob syntax), and marks unreadable or truncated coverage incomplete. File enumeration is not an atomic filesystem snapshot; a concurrently modified tree could invalidate containment checks between operations. A future source reader must recheck opened files before parsing. The committed lockfile pins TypeScript 6.0.3 and CI enforces typecheck on Node 22/24; this isolated local environment uses global TypeScript 5.8.3 for local checks.

The current AST parser records only syntactic module-import and const-alias facts. It does not prove bindings are the same under shadowing, mutated assignments, re-exports, wrappers or conditional imports. Syntax errors and dynamically constructed module specifiers are incomplete/unknown, not automatically supported. Location columns use TypeScript UTF-16 character offsets (1-based) and are not display-width indices. Source reader bounds byte size and enforces UTF-8, but concurrent filesystem changes cannot be excluded completely without stronger OS-level containment primitives.

Detection coverage is deliberately limited to a fixed set of proven SDK Horizon.Server construction/calls, known official Horizon HTTP hosts (`horizon.stellar.org`, `horizon-testnet.stellar.org`, `horizon-futurenet.stellar.org`) and certain fetch/Axios requests and response shapes. SDK imports alone do not generate a finding. Custom Horizon providers, Axios instances with dynamic baseURLs, wrappers, multi-module flows and alias chains beyond the safety budget can be missed. Uncertain SDK client configuration or Horizon-labeled HTTP parameters are marked incomplete where recognized; unknown functions or custom hosts cannot always be inferred as Horizon dependencies. `complete` means this bounded detector completed its declared scan, NOT that a repository is migration-ready or contains no Horizon dependencies. No measured accuracy on real repositories yet.

Rule categories provide documented migration considerations only. A `direct` mapping means an official mapping exists, **not** identical request/response contracts, history availability or transaction finality behavior. Classic payment/effect events depend on provider configuration and transaction meta, and unrecognized patterns fail closed to `unknown`. SDK builder calls do not necessarily reveal final resource filters; account builder mapping is explicitly `unknown`. The risk engine transforms static catalog hints into consistent migration-work review priorities while preserving separate evidence confidence; these remain heuristic triage, not final application impact scores. This library has no validated cross-app recall or precision, and a zero-finding report must never be called migration-ready.

Phase 06's `complete` result means only that the supported static pipeline reported no tracked coverage gaps; it does not imply all Horizon usage was detected, successful RPC migration, business safety or production readiness. `no-supported-evidence` is a coverage label, never approval. Severity prioritizes engineering investigation, not financial/security impact. Confidence assesses evidence applicability rather than migration success probability. Incomplete status takes precedence over any known finding. Existing detector blind spots, history retention, classic-event provider configuration and concurrent filesystem changes remain out of scope for proof.
